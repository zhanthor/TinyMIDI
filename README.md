# TinyMIDI

**Real-time guitar note detection on a microcontroller — no cloud, no phone, no host computer.**

TinyMIDI listens to a live guitar (or any monophonic instrument in its pitch
range) through a microphone wired directly to a microcontroller, classifies
the note being played with a quantized on-device neural network, and reports
it as either a Serial log line or a wireless MIDI Note On/Off event. The
entire pipeline — capture, spectral analysis, inference, and output — runs
locally on the chip in well under the width of a played note.

It targets two boards side by side from a shared model and feature front end,
built as a final project for **EE 446** (embedded / tiny machine learning):

| Target | Role |
| --- | --- |
| **ESP32** (I2S mic) | Primary demo target — fastest inference, ~31 updates/sec |
| **Arduino Nano 33 BLE Sense** (onboard PDM mic) | Hardware-comparison target — same model, ~3–5× slower core |

## How it works

```
mic capture (I2S / PDM)
        │  128 ms window, 16 kHz
        ▼
   2048-point FFT
        │
        ▼
log-frequency filterbank (217 bins, 3 bins/semitone)
        │  log + max-relative floor + mean subtraction
        ▼
   int8 quantize
        │
        ▼
TFLite Micro CNN  (Conv2D → MaxPool2D → Flatten → Dense → Dense → Softmax)
        │
        ▼
posterior smoothing / debouncing
        │
        ▼
  Serial log   and/or   MIDI-over-BLE (Note On / Note Off)
```

The classifier predicts one of **28 classes**: 27 discrete pitches spanning
MIDI notes 45–71 (roughly A2–B4, a standard-tuned guitar's practical range)
plus an explicit `silence` class. The feature front end is a **log-spaced**
filterbank rather than a linear FFT — a linear spectrogram packs every
fundamental in this range into the first few bins, which measurably hurts
separability at low pitches. The log-frequency rebuild fixes that at the cost
of a slightly longer analysis window (128 ms vs. an earlier 64 ms version).

Because the feature front end is gain-invariant by construction, no
microphone-level calibration step is required — only a coarse noise gate.

## Repository layout

```
TinyMIDI/
├── midi_note_esp32/       Firmware for ESP32 (I2S mic, primary demo target)
├── midi_note_nano33/      Firmware for Arduino Nano 33 BLE Sense (PDM mic)
├── project-slicer-fixed.ipynb        Slices GuitarSet audio into labeled,
│                                       leakage-safe training clips
├── TinyML_Final_Project_LogFreq.ipynb Trains, prunes, and quantizes the
│                                       model; exports the firmware headers
├── EE 446 - Instructions to Reproduce Model Training Data.pdf
│                                       Step-by-step data reproduction guide
└── LICENSE                            GPL-3.0
```

Each firmware folder is self-contained and holds an identical structure:

| File | Purpose |
| --- | --- |
| `model.h`, `model_params.h`, `filterbank.h`, `golden_test.h` | Generated by the training notebook; **identical on both boards** |
| `feature_provider.{h,cpp}` | FFT → log-filterbank → normalization |
| `fft.{h,cpp}` | Fixed-point-friendly FFT implementation |
| `note_recognizer.{h,cpp}` | Posterior smoothing and note debouncing |
| `audio_provider.{h,cpp}` | Microphone capture — **board-specific** (I2S on ESP32, PDM on Nano 33) |
| `ble_midi.{h,cpp}` | MIDI-over-BLE output |
| `midi_note_*.ino` | Board-specific sketch entry point |

That the model and feature-generation headers are byte-identical across
targets is intentional: retargeting the project to new hardware is a
capture-and-output problem, not a model problem.

## Model & training data

The model is trained on [GuitarSet](https://guitarset.github.io/), a public
dataset of annotated guitar recordings. `project-slicer-fixed.ipynb` slices
the raw recordings into fixed-length windows, keeping a window only if a
single pitch covers it almost entirely, and groups clips by source recording
so that near-duplicate, overlapping windows (a 128 ms window advancing in
32 ms hops shares 75% of its samples with its neighbor) can't leak across the
train/validation split.

`TinyML_Final_Project_LogFreq.ipynb` then:

1. Builds the log-frequency filterbank and turns each clip into a feature
   vector.
2. Trains a compact CNN, with optional pruning via TensorFlow Model
   Optimization.
3. Quantizes the trained model to int8 for TensorFlow Lite for
   Microcontrollers (TFLM).
4. Exports `model.h`, `model_params.h`, `filterbank.h`, and a `golden_test.h`
   reference vector, and drops them into both firmware folders.

Full, step-by-step reproduction instructions — including how to obtain and
prepare the raw dataset — are in **`EE 446 - Instructions to Reproduce Model
Training Data.pdf`**.

## Getting started

### 1. Generate (or reuse) the model headers

Run the two notebooks in order (slicer → trainer), or copy the four generated
headers from an existing run into the target firmware folder. Both firmware
folders expect the same four files.

### 2. Flash a board

<details>
<summary><strong>ESP32</strong> — I2S microphone, primary demo target</summary>

- **Library Manager** → `tflm_esp32` (Espressif's packaged esp-tflite-micro;
  the Cortex-M-only `Arduino_TensorFlowLite` will not compile for Xtensa).
- **Board:** ESP32 Dev Module.
- **Partition Scheme:** *Huge APP (3MB No OTA/1MB SPIFFS)* — the model plus
  the TFLM runtime exceeds the default partition.
- **Wiring** (INMP441 I2S mic): `SCK→GPIO14`, `WS→GPIO15`, `SD→GPIO32`,
  `VDD→3V3` (not 5V), `L/R→GND`.
- Serial Monitor at **115200**. A golden-vector self-test runs at boot and
  reports arena usage and pass/fail before it starts listening.
- `ble_midi.{h,cpp}` ships in this folder but is not yet wired into the
  sketch's `setup()`/`loop()` — Serial is the default output. Wiring in BLE
  MIDI here (following the Nano 33 build as a reference) is the natural next
  step, since the ESP32's inference speed makes it feel far more
  instrument-like than the Nano.

</details>

<details>
<summary><strong>Arduino Nano 33 BLE Sense</strong> — onboard PDM microphone</summary>

Must be the **Sense** variant — the plain Nano 33 BLE has no microphone and
will compile but capture nothing.

- **Boards Manager** → *Arduino Mbed OS Nano Boards*.
- **Library Manager** → `Chirale_TensorFlowLite`. If `Arduino_TensorFlowLite`
  is also installed, **delete it** — having both installed lets the Arduino
  builder resolve headers from one and link objects from the other, an ODR
  violation that can silently corrupt the build.
- **Library Manager** → `ArduinoBLE`.
- *(optional, recommended)* **Library Manager** → `Arduino_CMSIS-DSP`, then
  set `USE_CMSIS_DSP 1` in `feature_provider.cpp` — cuts feature-extraction
  time roughly 3–5×.
- **Board:** Arduino Nano 33 BLE. Serial Monitor at **115200**.
- MIDI-over-BLE is enabled by default (`ENABLE_BLE_MIDI 1`) and advertises as
  `TinyMIDI-Guitar` — **rename it** in `ble_midi.h` before demoing alongside
  other BLE-MIDI devices.
- The board does not reset when the Serial Monitor attaches, so boot
  messages can be missed — the onboard RGB LED reports status codes
  independently (solid green = running, red blink patterns = specific
  startup failures), and a `[alive]` heartbeat prints every 5 seconds once
  running.

</details>

### 3. Receive MIDI (BLE targets)

| Platform | How to connect |
| --- | --- |
| macOS | Audio MIDI Setup → Window → Show MIDI Studio → Bluetooth → Connect |
| iOS | Any BLE-MIDI host app |
| Windows | A BLE MIDI bridge (e.g. MIDIberry) + loopMIDI |
| Linux | BlueZ with the BLE-MIDI ALSA sequencer bridge |

## Measured performance

| | ESP32 @ 240 MHz | Nano 33 BLE Sense @ 64 MHz (portable) | Nano 33 BLE Sense @ 64 MHz (CMSIS-DSP) |
| --- | --- | --- | --- |
| Feature extraction | ~1.5 ms | ~17.5 ms | ~5 ms |
| Inference | ~9–11 ms | ~106–116 ms | ~21–23 ms |
| Update rate | ~31 Hz (32 ms hop) | ~15.6 Hz (64 ms hop) | ~15.6 Hz |
| Detection latency | 128 ms | 128 ms | 128 ms |
| Tensor arena used | — | 6.7 KB (of 32 KB allocated) | 6.7 KB |

Detection latency (time to recognize a newly struck note) is set by the
128 ms analysis window and is identical on both boards; the *update rate*
differs because a slower core can't finish inference before the next hop
arrives, so the Nano 33 build uses a longer hop to compensate. Both boards
run the model unmodified — the difference is entirely down to core speed and
whether CMSIS-NN's DSP-accelerated kernels are engaged.

Each board runs a **golden-vector self-test at boot**, replaying a canned
clip through the full feature-extraction and inference pipeline and diffing
the result against the value computed in the training notebook — a quick way
to confirm a port hasn't silently drifted from the reference implementation.

## Troubleshooting

Both firmware folders print a status code (via Serial and, on the Nano 33,
an RGB LED) for the most common failure modes: feature/model geometry
mismatches between the generated headers, an undersized tensor arena, a
failed microphone init, and BLE pairing issues. See the comments at the top
of each `.ino` and the per-file headers for the full list of causes and
fixes.
